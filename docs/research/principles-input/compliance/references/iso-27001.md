# ISO 27001 Engineering Rules

ISO/IEC 27001:2022 is the international standard for information security management (ISMS), with 93 Annex A controls across organizational, people, physical, and technological themes. Certification is voluntary and audit-based, not a legal requirement. This project builds toward it from the first line of code because EU/Dutch enterprise customers (vet chains, coops, suppliers) will demand it and the product handles farm operations, animal medication records, contact data, and automated actions taken on farmers' behalf. Every rule below is applied while writing code; no control is "added later".

## Secure development (A.8.25–A.8.34)

- Treat every feature that touches farm data, medication records, or automated actions as security-relevant and state its security requirements in the PR/spec before coding (A.8.26).
- Follow secure coding practice: validate and type all input at API boundaries, use parameterized queries only, encode output, never build SQL/shell/prompt strings by concatenation (A.8.28).
- Keep development, test, and production fully separated: separate environments, credentials, databases, and third-party API keys (sandbox keys outside prod) (A.8.31).
- Never use production farm data in tests or local dev; generate synthetic herds, animals, and contacts instead (A.8.33).
- Ship every change through a reviewed pull request with CI running tests, linting, dependency audit, and secret scanning; no direct pushes to main (A.8.32, A.8.29).
- Pin dependencies with a lockfile, run automated vulnerability scanning (e.g. dependabot/osv-scanner) in CI, and patch critical CVEs before other work (A.8.8).
- Define infrastructure as code with hardened defaults (deny-by-default network rules, no public buckets, TLS-only), and treat IaC changes like code changes (A.8.9, A.8.27).
- Restrict repository access and branch permissions; the repo is the source-code access control (A.8.4).
- Never commit secrets; load them from environment/secret manager, keep `.env` gitignored, and add a pre-commit secret scan (A.8.28).

## Access control & authentication (A.5.15–A.5.18, A.8.2–A.8.5)

- Enforce deny-by-default authorization on every backend endpoint: a farmer can only reach their own farm's data, checked server-side per request, never trusted from the client (A.5.15, A.8.3).
- Model roles explicitly (farm owner, farm worker, vet, mechanic, supplier, admin) and grant least privilege per role; external parties get scoped, farm-specific, revocable access only (A.5.18).
- Require strong authentication: MFA on the web portal and admin surfaces, short-lived access tokens with refresh rotation on mobile, and generic error messages that don't leak account existence (A.8.5).
- Give every user, service, and integration its own identity; no shared accounts, no shared API keys between integrations (A.5.16).
- Hash passwords with argon2id or bcrypt; never log, email, or store credentials or tokens in plaintext anywhere, including crash reports (A.5.17).
- Put admin/support functionality behind a separate privileged role with MFA, and log every use of it (A.8.2, A.8.18).
- Build deprovisioning as a first-class feature: revoking a worker's or vet's access takes effect immediately across API, portal, and offline sync (A.5.18).

## Cryptography & data protection (A.8.24, A.8.11, A.8.12, A.5.14)

- Enforce TLS 1.2+ for all transport (API, webhooks, integration calls) and reject plain HTTP; enable certificate pinning or strict cert validation in the mobile app (A.8.24, A.5.14).
- Encrypt all data at rest: database, backups, object storage, and the mobile app's offline database (e.g. SQLCipher / encrypted storage) (A.8.24).
- Store mobile tokens and keys only in the platform keystore (iOS Keychain / Android Keystore), never in shared preferences or plain files (A.8.24).
- Use vetted crypto libraries and platform primitives only; never implement custom crypto, and keep keys in a managed KMS/secret manager with rotation support (A.8.24).
- Mask or omit sensitive fields (medication details, phone numbers, addresses) in logs, error messages, analytics events, and LLM/automation prompts (A.8.11, A.8.12).
- Classify data in code: mark medication/treatment records and personal contact data as sensitive in the data model so serializers, loggers, and exports can treat them differently (A.5.12, A.5.34).

## Logging & monitoring (A.8.15–A.8.17)

- Emit structured audit logs for every security-relevant event: login, failed login, permission change, data export, sync conflict resolution, admin action, and every automated call/email/order (A.8.15).
- Make audit logs append-only and tamper-evident (no update/delete API on audit records), retained separately from application logs (A.8.15, A.5.33).
- Include who, what, when, from-where, and on-whose-behalf in each audit record, using UTC timestamps from NTP-synced servers (A.8.17).
- Add alerting for anomalies from day 1: repeated auth failures, unusual export volume, integration error spikes, and automated-action failures (A.8.16).
- Never log request bodies containing credentials, tokens, medication records, or personal data; log identifiers and hashes instead (A.8.15, A.8.12).

## Data lifecycle & backup (A.8.13, A.8.14, A.8.10, A.5.33, A.5.34)

- Implement automated, encrypted, versioned backups of all databases with a tested restore path; keep a restore-test script in the repo and run it on a schedule (A.8.13).
- Store backups in a separate account/region from production so one compromised credential cannot destroy both (A.8.13, A.8.14).
- Build hard deletion: when a farmer deletes data or leaves, purge it from database, search indexes, object storage, mobile caches, and (by expiry) backups, and record the deletion in the audit log (A.8.10).
- Design offline-first sync so deletions and permission revocations propagate to devices, and device-local data is wiped on logout/unenrollment (A.8.10, A.5.11).
- Keep medication/treatment records retrievable and immutable for their legal retention period (EU/NL veterinary record rules) before any deletion logic applies (A.5.31, A.5.33).
- Define RPO/RTO targets in `docs/security/continuity.md` and make infrastructure choices (replication, multi-AZ) that meet them (A.5.29, A.5.30).

## Third-party & supplier integrations (A.5.19–A.5.23)

- Before wiring any supplier API (vets, mechanics, suppliers, telephony, email, ordering), record it in `docs/security/supplier-register.md` with data shared, auth method, and DPA/security-terms status (A.5.19, A.5.20).
- Send each integration only the minimum fields it needs; never forward full farm or medication records to telephony, email, or ordering providers (A.5.14, A.5.19).
- Verify inbound webhooks cryptographically (signature/HMAC + timestamp) and treat all third-party responses as untrusted input (A.5.21, A.8.28).
- Isolate each integration behind its own module with its own credentials, timeouts, retries, and circuit breaker, so one compromised or failing supplier cannot cascade (A.5.22, A.8.27).
- Prefer EU-region processing for cloud and communication providers and record the region choice per supplier (A.5.23, A.5.34).

## Automated actions on the farmer's behalf (calls, emails, orders)

- Require explicit, revocable, per-action-type consent stored server-side before any automated call, email, or order is executed, and check it at execution time, not scheduling time (A.5.15, A.5.34).
- Make every automated action idempotent with a unique action ID, an amount/scope limit where money is involved, and a full audit trail of trigger, content, target, and result (A.8.15).
- Add a kill switch: a single flag per farm and globally that halts all automated outbound actions immediately (A.5.29, A.8.16).
- Require human confirmation for irreversible or high-value actions (orders above a threshold, medication-related communications) until an explicit risk decision recorded in the repo says otherwise (A.5.3).

## Incident readiness (A.5.24–A.5.28, A.6.8)

- Maintain `docs/security/incident-response.md` with detection sources, severity levels, containment steps (token revocation, kill switch, credential rotation), and EU/AVG breach-notification steps (72h to AP) (A.5.24, A.5.26, A.5.34).
- Build incident hooks into the code: feature flags to disable subsystems, forced logout/token revocation endpoints, and integration disable switches (A.5.26).
- Preserve evidence on incidents: never rotate or truncate logs during an investigation, and export relevant audit records before remediation (A.5.28).
- After any incident or near miss, add a post-mortem to `docs/security/incidents/` and turn each root cause into a test, lint rule, or rule here (A.5.27).

## Documentation for audit evidence (A.5.1, A.5.37, A.7.5 by hosting provider)

- Maintain a lightweight risk register at `docs/security/risk-register.md`; add an entry whenever a design decision accepts a security trade-off (ISMS clause 6.1).
- Keep an asset/data inventory at `docs/security/data-inventory.md` listing systems, data categories, and locations, updated when new stores or integrations are added (A.5.9).
- Document operational procedures (deploy, restore, key rotation, access review) as runnable scripts or step lists in the repo, not tribal knowledge (A.5.37).
- Rely on ISO 27001-certified cloud providers for physical security and record their certifications in the supplier register instead of building physical controls (A.7.x via A.5.23).
- Record quarterly access reviews (who has access to prod, repo, and admin) as dated markdown files in `docs/security/access-reviews/` (A.5.18).
